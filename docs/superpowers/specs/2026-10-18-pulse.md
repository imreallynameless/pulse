# Pulse

Approved direction: a separate MIT-licensed repository, first verify live Fitbit Air readings on Lei's Mac, then build an embeddable widget that others can fork and self-host.

## Milestone 1: local hardware verification
A dependency-free localhost web app in Chrome connects to the standard Bluetooth Heart Rate Service. Show BPM, connection freshness, number of notifications, interval median/p95/max, and optional RR intervals. Never simulate readings or claim sensor-to-screen latency from notification intervals. Export diagnostic data only on an explicit click; keep it in memory otherwise. No cloud publishing in this milestone.

Use Node 22+ for a loopback-only static server and node:test. UI: white (#ffffff), blue-grey canvas (#eef3f8), ink (#172b45), muted text (#52647b), berry accent (#b52650); system sans type, a large BPM reading and practical connection instructions. Simple responsive layout. No animation pretending to be actual beats.

## Milestone 2: after real hardware readings
Authenticated broadcaster sends every measurement over a persistent WebSocket to a relay. Per-feed public read-only iframe widget; stale/offline status, stop sharing, latest-only delivery, no historical database on the delivery path. Private publishing credentials never enter embed code. Include self-hosting and fork instructions and an MIT license. Measure receiver-to-widget delay separately from tracker processing delay. Implementation depends on first proving the hardware and deciding deployment destination.

## Hardware acceptance
Record 30–60 minutes of notification intervals, repeated readings, RR availability, disconnect/reconnect, tab background and Mac sleep behavior. No guarantee of continuous operation, 1 Hz updates, RR support or subsecond total latency until measured. User must enable sharing on their Fitbit and select it in the browser picker.

## Widget implementation decisions
Initial hardware connection produced valid notifications at approximately 1 Hz. Proceed with a browser broadcaster and a self-hostable Node WebSocket relay. A native companion remains future work.

Use explicit per-feed publisher tokens from PULSE_FEEDS JSON configuration; viewers only know a public feed slug. No hosted account system in v1. Publisher authenticates in the first WebSocket message, not the URL. Latest reading lives in memory, expires after 5 seconds, clears immediately on publisher disconnect. Each viewer gets remaining TTL, avoiding cross-device clock assumptions. Rate limit input and drop slow viewers rather than queue old readings. No database or mandatory external service.

The widget is /embed.html?feed=<slug> and uses a persistent same-origin WebSocket connection. Broadcaster explicitly starts/stops sending. The local first test sends only to loopback; actual internet deployment needs HTTPS and persistent WebSocket support. Add Docker and manual self-hosting instructions; no cloud account or paid deployment selected yet.
